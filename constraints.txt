# 依赖锁定（2026-11-02）
#
# 来源：干净的 Linux + Python 3.12 环境里执行
#     python -m pip install --no-cache-dir -r requirements.txt
# 得到的确切解析结果；随后用**这一套依赖**跑过：
#   · 全量 pytest：187 passed / 2 skipped（与本机 Windows 口径一致）
#   · tests/test_mcp.py 里两条 stdio 子进程用例重复 10 次：10/10 通过
#
# 用法（CI）：python -m pip install -r requirements.txt -c constraints.txt ruff
#
# 为什么要锁（不是洁癖，是真红过）：
#   requirements.txt 里除 mcp 外全是 `>=`，CI 每次跑都重新解析。2026-11-01 一次
#   **纯文档提交**（209ed02，只改 docker-compose 注释）让 CI 由绿转红 —— 代码一行没动，
#   是 pip 当天解析到的传递依赖变了（langchain-core 1.4.8→1.7.3、pandas 2.3.2→3.1.0、
#   pydantic 2.12.5→2.14.2、anyio 4.12→4.16 …），改变了 mcp stdio 关停的时序，
#   把一条**本来就带竞态**的用例稳定地照了出来（同一次运行里失败率约 50%）。
#   结论：CI 的绿不能依赖「今天 PyPI 解析到什么」。
#
# 升级流程（三步都要做，缺一不可）：
#   ① 改 requirements.txt 的范围；② 在干净 Linux py3.12 环境重新解析并更新本文件；
#   ③ 全量 pytest + test_mcp 的两条 stdio 用例重复跑 10 次，绿了再提交。
#   不要只改本文件里的单个 pin：单点升级正是「解析结果漂移」的来源。
#
# 说明：本文件只约束 CI 与本机复现；requirements.txt 的版本范围仍是「支持区间」的
